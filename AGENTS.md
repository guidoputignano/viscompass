# VIS PHARMA COMPASS — working agreement for AI agents

Read this before making any change. It exists because this project is
worked on by more than one AI agent (Claude Code and Codex, alternating),
plus the technical lead. Divergent assumptions between sessions are the
main source of wasted work here — not code quality.

`CLAUDE.md` is a symlink/copy of this file. Both tools read the same rules.

## What this product is

A **non-clinical, read-only management-analysis platform** for Italian
hospital pharmacy and regional pharmaceutical-expenditure governance,
built by bioERGOtech Foundation ETS. Buyers are Aziende Sanitarie (ASL)
and Regioni.

**The thesis — do not restate loosely, this exact framing has survived
many rounds of external review:** the platform does not generate the
savings. Loss-of-exclusivity savings are generated by patent expiry;
switching savings are generated by clinician and pharmacist decisions.
What the platform can defensibly cause is a **reduction in the delay
between an opportunity existing and the organization acting on it** — an
observable, contractually agreeable, third-party-verifiable indicator.

## Hard constraints

### 1. The regulatory boundary is permanent, not a current limitation

Every module outputs **aggregated, organizational-level data only**. No
module ever produces a per-patient recommendation, dose, or clinical
output. This is what keeps the platform outside EU MDR (Reg. 2017/745)
scope. Anonymization is *not* what keeps it out of scope — intended
purpose is.

The minimum aggregation level is the *struttura erogante*. Never build a
feature that computes, proposes, or checks anything for an individual
patient; under MDR Rule 11 that is out of contractual scope entirely.

Note the distinction between the *boundary* (permanent, in the product
documentation and contracts) and *defensive disclaimer copy in the UI*
(reviewed Sept 2026 as adding no value to a logged-in user — "Don't
share what it's not. Share only what it is"). Keep the boundary. Don't
plaster the interface with it.

### 2. Never fabricate a number

This project's credibility rests entirely on verified figures. Every
data claim carries a confidence tier:

| Tier | Meaning |
|---|---|
| `VERIFIED-EXACT` | Independently fetched/computed with code, exact match confirmed |
| `VERIFIED-SOURCE` | Source confirmed real, exact figures not recounted |
| `UNVERIFIED` | Reported by a source (including another AI agent) but not independently checked |
| `CORRECTED` | A claim found to overstate what independent checking confirmed |

Practical rules:

- Fetch the actual source, run the actual code, count the actual rows.
  Do not relay another agent's claim as settled fact.
- If a denominator or formula is missing, **omit the indicator** rather
  than approximate it. Precedent: the antibiotics module ships 3 of the 5
  standard OSMED indicators because the population denominator was not in
  the source files. It says so on the page.
- Synthetic/demo data must be flagged in the type system
  (`mode: "real" | "synthetic"`), labelled visibly in the UI, and never
  written to a production fact table. See `lib/dashboard-review/antibiotic-demo.ts`.
- Distinguish "no data available" from "zero" in every type, query, and
  UI state. `null` and `0` are different facts.
- Never invent testimonials, client logos, press mentions, or customer
  outcomes. The product is pre-launch.

### 3. Anonymization rules

- In every external-facing artifact, the four Abruzzo ASLs are labelled
  **ASL 1–4** with no Region named.
- Cross-ASL ranking must never expose another org's identity or values.
  This is enforced server-side by `my_objective_rank()`
  (SECURITY DEFINER, derives the caller's org from `auth.uid()`, never
  from a client parameter — `supabase_schema.sql` section 6). Do not
  reimplement this by fetching all rows and filtering client-side.

### 4. Access control is RLS, not application code

Row Level Security is the enforcement layer. Queries should simply ask
for the data and let the database decide. Do **not** add client-side
filtering as a substitute.

Known design points, already adversarially tested — don't "fix" these
without understanding them:

- A `regione`-type org sees every ASL in its `region_code`; an `asl`-type
  org sees only itself. This is what makes M6 work through RLS alone.
- INSERT policies constrain **values**, not just identity — a user cannot
  self-insert `status: 'approved'`, pre-answer their own feature request,
  or mark their own upload `reconciled`. This was a real escalation bug,
  found and fixed. Any new INSERT policy needs the same treatment.
- Approval, responses, and reconciliation results are written **only**
  via the service-role key server-side. There is deliberately no
  client-facing UPDATE policy on these tables.

## The gold file

`DIR_OSP_TRA_003AS_SellInSellOut_nuova_estrazione_2025.xlsx` is the
reference input format. Treat it as **Gold Sample v1**, not proof of a
universal Italian format.

Verified directly (2026-09-06):

- 1 sheet, 34 columns, **two header rows**, 13,116 data rows.
- **2025 only, ABRUZZO only.** Not national. Do not claim otherwise.
- 6 ASL codes: `130201`, `130202`, `130203`, `130204`, plus `ND`
  ("ASL non significativa", 50 rows), plus `130106` — a single row under
  a second, otherwise-unused code for Teramo (Traccia-only orphan,
  regional quantity 0 / Traccia quantity 63). Needs an explicit rule.
- Only **4,245 rows have all 12 months**. Partial coverage is the norm
  (8,871 rows), with 1,783 single-month rows. "Every row must have 12
  months" is an incorrect completeness rule.
- Contains `#DIV/0` cells, negative quantities/costs, extreme unit-price
  outliers, and repeated ASL–AIC–manufacturer combinations. These need
  documented handling rules, not automatic rejection.
- No formulas; results stored as values.

**Resolved ambiguity — do not re-raise with the stakeholder.** The two
header rows disagree about column 19. Header row 1 says
`DD + DPC + CO`; row 2's label says `(Distribuzione Diretta+Consumi
Ospedalieri)(a)`, omitting DPC. Tested across all 2,076 rows with
non-zero DPC: `DD + DPC + CO` equals the total in every case, `DD + CO`
in none. **The group header is correct; the column label is wrong.**

**Why this file matters strategically:** it is not merely a spend export.
It reconciles regional flows (DD + DPC + CO) against Tracciabilità/NSIS,
with variance columns for quantity, price, and cost already computed, and
flags for which source each record appears in. This is the M3 data the
project previously concluded had no public equivalent. Verified ingestion
and explainable discrepancy detection on the institution's own file is
the product's differentiator — not an algorithm count.

## Working conventions

- **`supabase_schema.sql` is append-only.** Schema changes are added as
  new numbered sections with DROP+CREATE migration blocks. Do not mutate
  earlier statements in place.
- **Commit messages carry rationale.** State what was verified and how,
  what was assumed, and what remains open. A 1,700-line commit with a
  one-line message was reverted within seven minutes; treat that as
  precedent.
- **Prefer several small, independently-revertible commits** over one
  large sweep, especially when the items are unrelated.
- **Verify before reporting.** "Type-checks clean" means `npx tsc
  --noEmit` was actually run. Claims about RLS behaviour mean policies
  were actually exercised against a real Postgres instance with real
  sessions, including adversarial cases — not read and reasoned about.
- **Fail loudly, never silently.** Loaders assert their column mappings
  at runtime and abort if a source file changes shape, rather than
  loading nulls. See `load_antibiotic_consumption.mjs`'s `assertLegend()`.
- **Ask rather than guess on business rules.** Unresolved definitions
  (ND ASLs, negative adjustments, duplicate keys, partial months,
  tolerances, Sell-In vs Sell-Out semantics) must be escalated, not
  invented.
- **Do not load department-level (UU.OO.) antibiotic rows** until the
  real legend for codes AL/DC/DM/EM/PN/PO/TI is supplied. Guessing
  clinical unit names is not acceptable.
- The technical lead's machine is Windows: prefer direct PowerShell
  commands over `.ps1` files (execution policy blocks them).
